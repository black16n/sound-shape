# 软硬结合说明

**分工原则：硬件做主角，软件做镜子。**

```
   ┌──────────────────────────┐
   │  ESP32  硬件（主）        │   INMP441 采声 → 512 点 FFT → 12 频带声纹
   │  · 本地识别，不依赖电脑    │   → 和 NVS 里的模板比余弦相似度
   │  · 按键录入新声音         │   → OLED 出名字 / 三色灯亮
   └────────────┬─────────────┘
                │ USB 串口，每行一个 JSON
                ▼
   ┌──────────────────────────┐
   │  bridge.ps1  串口桥       │   读串口 → POST /api/device/event
   └────────────┬─────────────┘
                │ HTTP
                ▼
   ┌──────────────────────────┐
   │  server.py   后端         │   存 SQLite（历史 + 设备声纹样本）
   │  · /api/device/event     │   通过 WebSocket / SSE 广播
   └────────────┬─────────────┘
                │ 推送
                ▼
   ┌──────────────────────────┐
   │  dashboard.html  大屏     │   实时显示：谁在响、什么时候、命中率
   └──────────────────────────┘
```

硬件**不依赖**电脑也能独立工作：识别、录入、删除全在板子上完成。
桥接只是把板子已经做出来的结果“翻译”给大屏看，顺便把声纹样本存进数据库。

---

## 启动顺序（三条命令，各开一个窗口）

```
1)  start_server.bat      →  http://127.0.0.1:5000
2)  start_bridge.bat      →  选串口（插上板子才有）
3)  浏览器打开 http://127.0.0.1:5000/
```

第 2 步必须**关掉 Arduino 的串口监视器**——串口是独占的，谁先占谁用。

## 硬件往上发的事件

每行一个 JSON，固件在 `Serial.printf` 里直接打出来：

| 事件 | 什么时候 | 内容 |
|---|---|---|
| `hello` | 开机 | `{"ev":"hello","tpl":3}` 告诉大屏"我上线了，有 3 个模板" |
| `hit` | 认出声音 | `{"ev":"hit","label":"门铃","conf":0.91,"gap":0.12}` |
| `miss` | 听到但没把握 | `{"ev":"miss","label":"水开","conf":0.52}`（2.5 秒限流） |
| `learned` | 录完一个声音 | `{"ev":"learned","label":"门铃","tpl":4,"bands":[12 个频带]}` ← **声纹样本本体** |
| `deleted` | 在管理页删掉 | `{"ev":"deleted","label":"门铃"}` |

`bands` 就是这份声纹的指纹（12 个频带能量占比），后端存进 `device_templates` 表。

---

## 后端新增

| 接口 | 作用 |
|---|---|
| `POST /api/device/event` | 接收上面五种事件 |
| `GET  /api/device/templates` | 查硬件上传过的声纹样本 |
| 表 `device_templates(name, bands, updated_at)` | 12 频带样本，和原有的 20 维模板分开存 |

`hit` / `miss` 会写进 `history`，`source='device'`，所以大屏的「识别历史」里能看出是硬件认出来的。

---

## 大屏怎么表现

- 硬件命中 → 主字变名字 + 闪一下 + 记录入表（和麦克风识别同一套反馈）
- 硬件录入新声音 → 右下角提示「硬件学会了「XX」· 样本已上传」
- 硬件开机 → 提示「硬件已连接 · N 个声纹模板」
- 名字不在前端模板库里也能显示（现场临时造一张卡，不会白屏）

## 怎么判断"连上了"

"没反应"可能是五段里任意一段断了。跑一次体检：

```
双击 check_link.bat
```

输出长这样，断了哪段一眼就看出来：

```
  1  后端服务            OK  已启动 v1.0.0
  2  串口设备            OK  COM5   当前用 COM5
  3  串口有数据          OK  收到 3 条 JSON，例如 {"ev":"hello","tpl":4}
  4  后端收到硬件        OK  0.5 秒前收到 hello（累计 1 条）
  5  大屏已连接          OK  1 个客户端在线

  全链路正常。对着板子拍一下手，大屏应该跳出名字。
```

### 五段分别是什么

| # | 检查什么 | 通了说明 | 断了先看 |
|---|---|---|---|
| 1 | 后端在跑 | `server.py` 起来了 | 双击 `start_server.bat` |
| 2 | 系统认得到串口 | USB 线、驱动没问题 | 插紧线；CH340 装驱动 |
| 3 | 板子在往外发数据 | 固件在跑、波特率对 | 按复位键；确认 115200 |
| 4 | 桥把数据送到了后端 | 桥在跑、HTTP 通 | 双击 `start_bridge.bat` |
| 5 | 浏览器连着后端 | 大屏会实时刷新 | 打开地址并刷新页面 |

### 三个细节

**第 3 项显示"被占用"是正常的** —— 说明桥已经在读串口了，这时候用第 4 项判断。

**第 4 项比第 3 项更有说服力** —— 它绕开了串口，直接从后端问"最近 45 秒内有没有收到硬件上报"。只要它是 OK，说明整条链路（板子→串口→桥→后端）都通了。

**第 5 项为 0 不代表硬件有问题** —— 那只是浏览器没开。

## 三十秒手动确认

不想跑脚本的话：

1. **看板子屏幕**：OLED 亮着、显示"静" → 固件在跑
2. **看桥的窗口**：每有声音就刷一行 `HIT 门铃` → 桥在转发
3. **看浏览器右上角**：连接状态是绿的 → 大屏连着后端
4. **拍一下手**：大屏跳名字 → 全链路通

四个都看到，就是连上了。

## 不接板子也能验证后半段

不接板子也能验证后半段：

```powershell
# 模拟硬件上线
curl.exe -X POST http://127.0.0.1:5000/api/device/event -H "content-type: application/json" -d "{\"ev\":\"hello\",\"tpl\":3}"

# 模拟一次命中
curl.exe -X POST http://127.0.0.1:5000/api/device/event -H "content-type: application/json" -d "{\"ev\":\"hit\",\"label\":\"门铃\",\"conf\":0.91}"
```

大屏应该立刻跳出「门铃」。

## 故障对照

| 现象 | 原因 | 处理 |
|---|---|---|
| 桥说"没有找到串口" | 板子没插 / 缺 CH340 驱动 | 插好线，装驱动，看设备管理器 |
| 桥说"打不开 COMx" | 串口被 Arduino 监视器占着 | 关掉 Arduino 串口监视器 |
| 桥转发失败 | 后端没起 | 先跑 start_server.bat |
| 大屏没反应但桥有输出 | 前端没连上 WS | 刷新页面，看右上角连接状态 |
| 中文变成问号 | 编码没设对 | bridge.ps1 里已经设了 UTF-8，Windows 终端再执行一次 `chcp 65001` |
